# B：虚拟冷热需求到供暖目标协议 v1

2026-10-27实施前固定。范围为已有住宅、两位虚拟住户A/B、确定性规则；不新增模型或场景，不改变已冻结研究控制器。这里的需求是**供暖设定值意图**，不是测得的热感觉、人员舒适区间或期望室温的可靠反演。

## 映射及优先级

- 提交时记录操作者基准`base_C`，之后不随滑块变化反复累加：“更暖”→供暖目标≥基准+0.5°C；“更凉”→目标≤基准−0.5°C；“保持”→目标等于提交时基准。0.5°C是本版交互约定，不是生理学估计。
- 显式目标为单点，显式区间为闭区间；允许提交5～40°C内的有限数值，以便明确表示超出执行器能力的有效意图；反序/非有限/类型错误输入拒绝。相对需求的基准限18～23.25°C。
- A/B等权。有共同可执行区间时，选择该区间内最接近操作者当前基准的值，不对互相冲突的需求求平均。
- 机械动作范围18～23.25°C、0.5K/15分钟限速与原停止带始终优先。操作者裁决不能覆盖机械限制。共同意图区间为空为冲突；与执行器范围无交集为目标不可执行；限速导致本步达不到目标单独记录，不等同请求非法。
- 默认不裁决：冲突/不可执行时不下发动作、不推进时间，保留会话等待处理。操作者可明确选择A、B或基准；被覆盖的需求仍保留并计入未满足项。裁决只对所确认的需求版本有效，提交/撤销/过期后不能继续偷偷沿用旧裁决。

## 生命周期

- 新提交替换同一住户旧请求，保留事件账本；撤销立即生效，不推进仿真。每次变更递增需求版本，旧页面的提交/推进确认被拒绝。
- 请求只属于本次会话，新会话从空请求开始。历史按仿真时刻与账本顺序显示，同一时刻以最后一次变更为准；每步控制使用的快照另外保存在该步事件中。浏览历史不修改待提交草稿。
- 有效期1～16个900秒时间步（15分钟～4小时）；使用半开区间`submitted_s <= t < expires_s`。暂停不消耗仿真有效期；引擎自身空闲失效按既有恢复逻辑另处理。
- 期限在提交时固定。批量快进逐步检查，不能每步重新提交/续期；到期或撤销后回到剩余有效需求或操作者基准，不复活历史请求。
- “按需求”模式执行上述映射；手动和演示规则保留为显式旁路，说明未采纳人员需求。旧schema1记录及旧`preferences`字段保持原来被动记录语义，不追溯当作新请求。

## 能力与记录

- 降低供暖目标只能减少供暖，没有主动制冷能力。当前温度偏高时给出该限制，不保证达到室温目标或恢复真实舒适；不修改人数、人体散热或官方温度日程。
- 保存提交/替换/撤销/过期事件、锚定基准、有效期、需求版本、裁决、每步有效需求快照、映射目标、限速下发及实际测量。单独核对各人的**设定值意图偏差K及区间积分K·h**，不与官方操作温度越界混用，不称为人员不舒适量。
- 同起点规则对照重建热仿真并回放同一需求时间序列/快照，保留相同期限；规则仍不采纳需求，因此属于工程对照，不是同等人员需求满足条件下的节能证明。

## 本轮验收门

固定单人/同向、兼容区间、冲突、显式裁决、撤销、精确到期、批量不续期、版本过时、越过机械范围、限速未满足及无制冷提示案例。冲突拒绝不能使健康仿真进入错误或偷偷推进；对照中有效请求与期限一致；旧接口和历史文件不变。先离线测试，再在旧day63做短程真实工程验收及浏览器操作，不作为新训练/校准/盲评数据。

## API与复核入口

- `POST /api/demand`：`person/kind/base_C/ttl_steps/revision`；target另带`target_C`，range另带`lower_C/upper_C`。
- `POST /api/demand/revoke`：`person/revision`；变更接口只在有活跃住宅、暂停且版本一致时接受。
- `POST /api/demand-preview`：`base_C/resolution`，只读返回共同区间、可执行区间、目标、阻止原因、能力说明及版本，不推进仿真。
- `/api/advance`的needs意图还须带`resolution/demand_revision`；manual/rule保留旧三字段接口。无裁决冲突、旧确认返回409，输入格式错误返回400，均不得推进或关闭健康会话。
- `demand_summary`和每步`demand_evaluation`记录的是设定意图偏差，不能混入官方KPI或当成个人舒适预测。schema2保留原生轨迹/官方KPI核验；schema1只读回放继续支持。
