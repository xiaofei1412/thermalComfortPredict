# 本地房间工作台 V0.1

目标是让你亲自操作一个房间，看到真实仿真反馈并留下可追溯记录。工作台连接已有BOPTEST；B阶段加入[确定性人员意图协议](demand-protocol.md)，不训练新模型或改变已封存的研究结论。

## 启动

在项目根目录的 PowerShell 中运行：

```powershell
# 首次安装，沿用CPU研究环境；已有环境可跳过以下安装命令。
py -3.14 -m venv .venv
./.venv/Scripts/python.exe -m pip install torch==2.10.0 --index-url https://download.pytorch.org/whl/cpu
./.venv/Scripts/python.exe -m pip install -e .
# 已部署过 BOPTEST 时，先检查服务；首次部署见下方协议。
./scripts/setup_boptest.ps1 -Action status
# 如果服务没有运行：
./scripts/setup_boptest.ps1 -Action up
./scripts/start_workbench.ps1
```

打开 <http://127.0.0.1:8765>。终端保持运行，Ctrl+C退出；先在网页结束会话可立即释放仿真工作进程。启动器依次查找`.venv-cpu`和`.venv`，也支持`-PythonPath`指定已有解释器；不会自动安装依赖。安装步骤见[基线协议](experiments/baseline.md)；BOPTEST需要已有WSL/Docker，部署见[仿真协议](experiments/simulation.md)。网页不需要Node、前端构建或外网字体。

同工作区重复运行启动器会显示已有URL；其他工作区/未知服务占用端口时不会接管，可显式指定`-Port`。Python直接入口在端口被占用时以状态码2退出，Windows使用独占监听防止两个进程分享端口。本次A阶段修复服务运行在<http://127.0.0.1:8768>，可用`./scripts/start_workbench.ps1 -Port 8768`复用。当前交付支持在源码目录运行/editable安装，未声明wheel独立分发；资产和发布缺口见[交付范围](delivery-scope.md)。

复用已有服务不会热更新Python代码。修改源码后，应先结束会话、退出原进程再启动；无法退出时可选空闲端口，但不要同时开展多个实时仿真任务。

服务器只监听本机，不开放外网访问。当前只有一个BOPTEST worker，不要同时运行另一份工作台或研究采集脚本。启动工作台本身不要求BOPTEST在线：已有会话仍可回放，创建新仿真时才检查引擎。

## 一次完整体验

1. 选择早春、暖季或晚秋，新建会话。它们复用既有演示日期day63/147/315，统一08:00起步、七天预热，不是新的独立研究留出。
2. 默认“按需求”模式：点击住户A/B，选择“更暖／保持／更凉”，再点击“提交”；展开“目标、区间和有效期”可输入显式目标/区间和15～240分钟有效期。相对需求锚定提交时基准±0.5°C，不自动累加；“保持”固定该基准。提交本身不推进时间。虚拟意图不是实际热感觉标签，不改变人数或人体散热。
3. 预览共同可执行区间及映射目标；不冲突时选最接近操作者基准的值。冲突或超出机械范围时按需求推进被阻止，可修改/撤销，或显式选择A、B、基准；被覆盖请求继续记为未满足，不能通过裁决突破18～23.25°C或限速。点击“推进15分钟”才执行动作；有效期按仿真时间计算，快进不续期，版本变化后旧裁决失效。
4. 观察实际操作温度、实际供暖设定、电功率和供暖动画；点击热泵查看热功率与电功率的区别。满足供暖设定意图不等于实际室温或真实舒适已达标；房间为均匀单热区示意。降温请求会提示仅能减供暖、不能主动制冷。
5. “手动”和“演示规则”是明确旁路，不采纳请求；界面和记录标识旁路。支持快进4小时、步后暂停，每会话最多24小时。撤销立即生效，事件记录可查看提交/替换/撤销/过期及版本。
6. 结束保存后选择历史会话、拖动时间点或播放、导出JSON。回放不触碰仿真；旧被动preferences字段不会被追溯激活。新会话清空请求，查看历史不改变待提交草稿。
7. 对已结束的原始会话运行“同起点规则对照”。服务重新初始化，核对初始测量/时长/天气，并逐步回放相同需求快照及期限。规则仍不采纳请求，所以不能据耗电差宣称同等需求满足下节能。设定意图偏差积分另列，不与官方温度越界混用。

## 执行与指标边界

- 对象固定为BOPTEST0.9.0 `bestest_hydronic_heat_pump`、192m²、供暖执行器。无制冷、风量或开窗控制。
- 供暖目标18～23.25°C，每15分钟变化不超过0.5K。演示规则复用早期`simulation.rule_action`的占用/非占用偏移0.5/3K，再加温度保护与同样限速；不是冻结的恢复规则或太阳MPC。低于日程下界+0.2K时请求最大供暖，高于上界−0.2K时请求最小设定，其余跟随日程。
- 操作温度18～35°C只是停止带，不是舒适区或安全证书。手动控制可以违反官方温度日程；界面显示越界，不承诺自动恢复舒适。供暖设备不能解决暖天气过热。
- 每个15分钟步读取31个原生30秒点，检查时间、实际动作及非负电功率。电量积分热泵、风机、水泵电功率，温度越界按官方日程计算K·h；结束后核对BOPTEST官方能耗、越界、费用与排放KPI。另行评估供暖设定意图偏差，不把它当作真实人员舒适评价。
- 这些演示从08:00开始，部分时段官方区间是15～30°C。规则可能几乎不供暖，因此“同样零日程越界”不能证明住户同样满意，更不能据此宣称节能算法成功。统计对照只是本段仿真的读数。
- MPC、热感觉/冷热偏好预测模型均未接入第一版。办公室只读展示原封存边界，后端拒绝创建办公室仿真；真实楼宇闭环及Sim-to-Real未实现。

## 保存与故障处理

原始会话在`outputs/workbench/sessions/<id>.json`，包含初始状态、引擎/场景/单位、源码与页面哈希、逐步意图/下发/实际响应、原生采样、天气日程、累计指标和官方KPI核对。每个成功步原子写入；输出与研究数据隔离且不提交Git。`GET /api/download/<id>`导出同一完整记录；列表和界面状态省略大体积原生数组。

B阶段新会话使用schema2，增加需求事件账本、版本、绝对仿真期限、逐步决策快照和分人设定意图偏差积分。相同时刻的提交/撤销在历史界面显示该时刻最终状态，具体动作使用的版本以步记录为准；旧schema1仍可回放，对照不追溯激活旧被动偏好。完整字段及接口见[需求协议](demand-protocol.md)。

进程重启后只恢复历史阅读，不恢复FMU状态。不要用一份JSON冒充实时状态。超时或测量失败会停止会话并尝试释放worker，不自动重试可能已经生效的`advance`。最后成功步可继续回放；失败调用后的物理状态不确定，不作为有效轨迹。若释放失败，界面提示再次“结束”；引擎的空闲超时也可能使长时间暂停的会话失效，此时重建会话，不伪造续跑。强制结束Python进程无法保证即时释放引擎。

引擎明确返回该testid无效时，会话标为`interrupted`，保留有效轨迹并允许新建，不补造最终KPI；其他400错误或超时仍保留ID供释放重试。初始化列表按0步显示，异常/未完成历史带状态标识。服务断线时显示“最后已知状态”并禁用控制，恢复连接不自动重发动作。Ctrl+C退出仍未正常结束的会话会标记`interrupted`，需最终KPI时请先点击网页“结束并保存”。
